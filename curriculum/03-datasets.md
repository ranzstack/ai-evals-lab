# 03 — Building good datasets

> **Big idea:** Your eval can only be as good as its cases. Most of the
> value, and most of the work, is in choosing *what to test*.

## Where cases come from (best to worst)

1. **Real production data**: actual tickets, queries, and conversations (anonymized). This has the most realistic distribution.
2. **Real failures**: bug reports, thumbs-down feedback, support escalations. These are the highest-value cases you can get.
3. **Expert-written cases**: domain experts write cases that target known hard spots.
4. **Synthetic cases**: generated by an LLM from a description of the input space. Useful for coverage and volume, but always review a sample by hand, because synthetic data tends to be cleaner and more uniform than reality.

## Coverage: think in dimensions

List the ways inputs vary, then make sure you have cases across each dimension. For triage:

- **Category**: billing, bug, feature, account, other
- **Difficulty**: easy, ambiguous, multi-issue, misleading ("it's a bug that…" for a feature request)
- **Tone**: calm, angry, false urgency
- **Language**: English, Spanish, French…
- **Length**: one word ("help"), rambling paragraphs
- **Adversarial**: prompt injection ("ignore all previous instructions…")
- **Policy-sensitive**: refund requests, security incidents, legal requests (GDPR)

Look at the `tags` in `labs/data/tickets.jsonl`. Which dimensions have only **one** case?
One case per slice can't tell you much (see Module 5).

## Ground truth is harder than it looks

- **Ambiguity.** Is "I upgraded but don't see the features" billing or account? If your experts disagree, either allow both (`acceptable`) or sharpen your definitions. **Disagreement among labellers is a signal about your spec, not noise to average away.**
- **Label errors.** Re-derive a sample of labels yourself. Public benchmarks often carry a few percent of wrong labels, and yours will too.
- **Where did the labels come from?** If "expected" outputs were produced by the current model, your eval rewards *imitating that model*, not being right. Never use model A's outputs as gold when comparing A vs B.

## Leakage and shortcuts

- **Leakage:** the expected answer, or a hint to it, appears in the prompt, the few-shot examples, or the tool descriptions.
- **Shortcuts:** could a dumb baseline score well? The lab's mock model is keyword rules, and it gets ~95% on category for the dev set. That tells you the dev set's category labels are too easy (too keyword-aligned) to tell a smart system from a dumb one.

## Dev set vs holdout (test) set

- **Dev set**: you look at it, iterate on it, and fix failures against it.
- **Holdout set**: you run it rarely, and you never tune against it. It exists to catch **overfitting**, where your prompt has learned the dev set rather than the task.

The lab has `tickets.jsonl` (dev, 20 cases) and `tickets_holdout.jsonl` (holdout, 8 cases).

## How many cases?

There's no magic number, but useful rules of thumb:
- **20–50** cases are enough to start, and to catch big regressions.
- **100–300** cases let you detect ~5–10 point changes with reasonable confidence.
- Coverage of important slices matters more than raw count.

Start small and grow the set from real failures.

## As a lead engineer

- **Ownership:** who owns the golden dataset? It should have an owner and a review process, just like a schema.
- **Labelling guidelines:** write them down (e.g. "urgent = production outage, security incident, or data loss"). This document is often more valuable than the eval code itself.
- **Privacy:** production data in eval sets needs the same care as production data anywhere else. Anonymize it, and check retention rules.
- **The failure → test-case loop:** make "add a regression case" part of your incident and bug process for AI features.
